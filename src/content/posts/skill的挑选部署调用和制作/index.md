一、金句 Skill 并不是装得越多越好。

SKILL.md 是一个总目录，它负责告诉 AI 现在进行到哪一步了，需要去读取哪一份详细的规则。

纯文字的描述对 AI 来说太抽象，直接把素材放进去，AI 执行准确性就会大大提高。

二、分点干货 用同一个 Agent、同一项任务做对比，不加 Skill 生成三张封面图，再调用 Skill 用同样提示词生成一次，可以看到加了 Skill 的质量明显更好，更贴合个人审美，结果也更稳定更标准，排版、字体、整体风格都比较一致。

用 Skill 的作用主要有两个，一是在做自己不擅长的工作时，直接用成熟的 Skill 可能比自己做得更好、质量更高，二是在做重复性工作时，Skill 可以让任务完成得更标准，还不需要跟 AI 反复沟通、反复输入大量提示词去调教它。

Skill 翻译成中文就是技能，不能简单理解成提示词或一份操作 SOP，用厨师打比方，一个做菜技能里包含一套做菜流程，比如备食材、准备调料、起锅烧油、先炒肉后炒菜、最后放调料，这是操作顺序，还包含每一步的标准，比如选哪个部位的肉、肉丝切多长多宽、调料比例多少，让做事更准确，此外还会带上自己惯用的调料和锅具，有了这些才能又快又好吃，Skill 也是一样，就是给 AI 做事的流程和标准，再加上任务用到的工具和素材，目的是让 AI 做事又快又好。
![image.png](https://cdn.jsdelivr.net/gh/rhx225522/picgo-bed@main/img/20261123093855545.png)


想让发挥不稳定的学徒稳定做出好菜有两种方法，一种是他每次做的时候都盯着，手把手一步步教会，这就是传统用 AI 的方式，反复对话、不断调试、一直盯着执行，另一种是直接把做菜的经验、流程和标准写成菜谱给他，让他按菜谱一步步做，这就是调用 Skill 的方式，让 AI 照着工作手册认真执行。

Skill 本质上是以文件夹的形式存在电脑里，里面最核心的文件叫 SKILL.md，是不可或缺的主文件，最上方有两项内容，name 是 Skill 的名字，description 是 Skill 的描述，用来告诉 AI 这个 Skill 到底能做什么、遇到什么任务时应该调用它。

description 这段描述非常重要，写得太模糊，AI 可能根本不知道什么时候该调用，写得太宽泛，AI 又可能在不该调用的时候触发，如果 Skill 经常无法被准确调用，多半就是这段描述出了问题。

SKILL.md 里首先要写清楚 Skill 的工作边界，比如它可以处理口播视频，但如果只是想压缩视频、提取视频字幕，或者明确要求使用其他动画工具，就不应该调用这个 Skill，接着写执行流程，比如拿到视频后先检查原始素材、保存原文件、清理气口、转写字幕，再让用户确认视觉风格，做一小段真实动效演示，确认以后再进入完整制作，制作完还要检查文字有没有重叠、动画和音频有没有同步、视频能不能正常播放，最后把成片和相关文件一起交回，也就是把任务先做什么后做什么、哪个地方必须确认、什么状态才算完成全部整理清楚。

标准的 Skill 除了 SKILL.md 主文件外还会配几个辅助文件夹，第一个是 references 参考说明，SKILL.md 规定流程，references 里写流程中每一步的标准，包括剪辑工具的工作标准、检查视频清理气口转写字幕预览渲染用到的具体命令、视觉标准、字体排版配色标准、动画节奏以及画面如何跟音频同步，内容太多不可能都塞进总文档，就分别放进 references。

第二个文件夹是 scripts，里面放 AI 需要用到的程序，如果说 SKILL.md 是流程、references 是标准，scripts 就是提供给 Agent 的工具，相当于厨师为做好某些菜品自备的特殊厨具，比如给原始视频建立识别编码、把剪切方案和素材绑定避免剪错，以及检查字幕和语音是否对齐的工具，都是提前写好、执行任务时一定会用到的。

第三个文件夹是 assets，里面放给 AI 的素材，相当于厨师自己带的调料，前面内容都是纯文字描述，对 AI 来说太抽象，做出来的东西很容易跑偏，直接把素材放进去，执行准确性会大大提高，比如放不同的风格模板让 AI 直接调用，结果就八九不离十。

SKILL.md、references、scripts、assets 这四个就是一套 Skill 的标准目录，AI 调用时先读取 SKILL.md 的工作流程，按流程一步步执行，每做一步查阅 references 里的工作标准，同时调用 scripts 里的工具，参照 assets 里的模板，最终完成任务，这套设计的核心原则叫渐进式加载提示词，工作做到哪一步，再让 AI 去看哪一段的提示词。
![image.png](https://cdn.jsdelivr.net/gh/rhx225522/picgo-bed@main/img/20261123093957232.png)

并不是每个 Skill 都必须有复杂结构，有的很简单的 Skill 就是一份 SKILL.md 文档，这是最小单位的 Skill，同样可以顺利完成一个任务。

安装 Skill 有两个副作用，第一个是会增加 AI 单次执行任务的时间和 token 消耗，AI 开始处理任务时会先读取自己到底有哪些 Skill，读取的不是全部文件内容，而是 name 和 description，再通过描述判断当前任务要不要调用，这就像学徒做饭前要先翻菜谱目录找对应菜品，如果菜谱只有五道菜可以轻松找到，有五百道菜的话光看完目录就非常消耗时间和脑力。

第二个问题是 Skill 装得越多，调用的精准性和执行效果有可能下降，装了两三个功能相近的 Skill，它们的 description 写得也比较相似，AI 自动调用时就很难准确识别这项任务到底该调用哪个，就像菜单上同时出现两道鱼香肉丝，一个叫招牌鱼香肉丝，一个叫必点鱼香肉丝，却没有明确说明区别在哪里。

判断一个需求适不适合做成或选用 Skill，第一个标准是长期反复执行、流程标准相对固定，比如每日工作日报的格式、写法、口吻固定，电商产品图的风格样式统一、仅产品不同，这类就可以把流程和标准交给 Skill。

第二个标准是使用 AI 时反复出现的痛点，长任务里总要一次次把标准交代清楚，比如常见的 Planning-with-Files 这类场景，反复重复的要求和痛点就值得沉淀成 Skill。

找适合自己的 Skill 要从实践中发现自己的痛点和需求，渠道包括各家 Agent 软件内置的 Skill 板块，SkillHub 这类技能市场，里面内容应有尽有，以及 GitHub 上开源、可以免费使用的 Skill，数量非常多。

部署安装后要先了解这个 Skill，确认它已经保存在本地的路径，以及已确认包含哪些文件，比如 SKILL.md、references、assets、agents，它会在下一轮对话中可用。

Skill 的触发方式有两种，一种是自动触发，靠 description 和当前任务场景匹配，比如明确点名调用这个 Skill，请求生成中文文章配图或文章插图，请求设计配图方案和 shot list，提到小黑、怪诞、手绘、正配图，要把抽象观点、流程、状态或隐喻画出来，或者编辑已有图片比如去掉标题、修改文字、增强怪诞感。

另一种是手动触发，就是自己明确知道有哪个 Skill、要用哪个 Skill 去做任务，直接在输入框选择该 Skill，再加上具体的任务指令。

Skill 把频繁重复的工作沉淀成可反复调用的工作流程以提升效率，也能处理原本自己不太擅长的工作，是 AI 小白进阶过程中一个明显的分水岭。

三、行动清单 拓展资料可以先读 Anthropic 官方的 Agent Skills 文档，重点看 SKILL.md 的结构规范、name 与 description 的写法要求、渐进式加载的设计原则，以及官方给出的示例仓库。

拓展资料可以翻阅提示工程指南中关于系统提示、任务拆解、输出格式约束的章节，理解 Skill 本质上是被固化下来的一套高质量提示词与流程约定。

拓展资料可以在 GitHub 上检索主流的 agent skills 开源集合，挑三五个不同类型的仓库，对照目录结构看别人如何划分流程、标准、工具和素材。

可延伸了解的概念是渐进式加载，上下文窗口容量有限，不可能把全部规则一次塞进模型，按需读取对应片段可以降低干扰、提高执行准确率，这是 Skill 目录分层的核心依据。

可延伸了解的概念是经验显性化与流程固化，把自己脑子里隐性的判断标准、操作顺序和验收条件写成明确规则，反复出现的个人偏好才能被稳定复用。

可延伸了解的概念是 Skill 路由与语义匹配，description 相当于技能的标题和摘要，模型先做语义匹配再决定是否加载完整内容，描述的区分度直接决定召回和命中率。

可延伸了解的概念是上下文工程，研究哪些信息应该进入模型上下文、哪些放在外部文件按需读取，和 Skill 的渐进式加载思路一脉相承。

可延伸了解的概念是单一职责与模块化，一个 Skill 只覆盖一类边界清晰的任务，功能相近的 Skill 要在描述里写清差异，避免互相冲突和误触发。

可延伸查阅的材料包括 Anthropic Agent Skills 官方文档与示例项目，各家 Agent 平台关于自定义指令、自定义工具和技能安装路径的说明，以及检索系统中标题摘要与召回相关性的公开资料，可迁移理解 Skill 描述的匹配逻辑。

练习方案可以先盘点自己一周内重复让 AI 做的任务，按出现频率和流程标准的固定程度排序，挑出第一个最值得沉淀的高频任务。

练习方案可以为一个现有 Skill 重写 description，分别写清什么时候使用、什么时候不使用，再准备十个应该触发和十个不应该触发的场景跑一遍，记录命中率和误触发情况。

练习方案可以拆解一个开源 Skill 的目录结构，逐份文件标注哪部分属于流程、哪部分属于标准、哪部分是工具、哪部分是素材，对照自己的任务模仿搭建。

练习方案可以把一段每次都要重复粘贴的长提示词整理成 SKILL.md，先做只有一个主文件的最小版本跑通任务，确认稳定后再把细分标准拆到 references，把可复用脚本放进 scripts，把模板样例放进 assets。

练习方案可以建立调用失败记录，每次出现没召回、选错 Skill 或参数用错的情况都记下来，回流修改描述、边界和示例，再回归测试。

练习方案可以定期整理自己的 Skill 列表，删掉重复、过期和长期不用的条目，控制同时挂载的数量，减少菜单过长带来的路由干扰。
